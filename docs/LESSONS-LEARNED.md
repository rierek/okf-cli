# LESSONS-LEARNED — okf-tools

Additive log. Each entry: Symptom · Fix · Forward-Guard.

## LL-01 (2026-07-25, P6 okf-cli-asky) — env-var pinning dead due to import-time binding

- **Symptom:** Boundary tests pinned the CLI under test via `os.environ["OKF_CLI"]` in `setUp`, but `mcp/okf_mcp.py` binds `OKF_CLI = os.environ.get(...)` as a module global at import time — the tests silently exercised the main-repo CLI copy instead of the worktree copy; a broken worktree CLI kept them green.
- **Fix:** Patch the module attribute directly (`mcp.OKF_CLI = ...`) in `setUp`, restore in `tearDown` (commit `5a25ac6`).
- **Forward-Guard:** Every test that pins a target-under-test MUST prove itself with a mutation self-test (break the target, watch the test fail, revert byte-identically) before it counts as evidence. Reviewer caught this only because the review protocol mandates independent mutation probes.

## LL-02 (2026-07-25, P2 okf-cli-ez6f) — false "file does not exist" claim propagated into bean ERRATA

- **Symptom:** Implementer recorded in the bean that `EVAL-DESIGN.md` "does not exist anywhere" and suggested authoring it; the file exists at `~/Obsidian/Vault/okf-revision/EVAL-DESIGN.md` (exactly where the milestone bean's Think-collection pointer says). Follow-up task owners acting on that note would have duplicated the design doc.
- **Fix:** Reviewer verified the real path; supervisor appended a dated ERRATA correction to the P2 bean and preludes into P3/P4 beans.
- **Forward-Guard:** Negative existence claims ("X does not exist") in bean closures require the search scope quoted (where was looked). Consumers of a bean must treat un-scoped negative claims as unverified.

## LL-03 (2026-07-25, P5 okf-cli-5qmn) — stopped agent left fixture residue in the real catalogue

- **Symptom:** The P5 implementer was stopped by the user mid seed/teardown window; `_okfeval-s1..s4.md` stayed behind untracked in the live Knowledge-Catalogue.
- **Fix:** Supervisor ran `python3 cli/eval/fixtures.py --root ~/Obsidian/Knowledge-Catalogue --teardown` (idempotent by design, P2 acceptance) and verified `git status --short` clean.
- **Forward-Guard:** After ANY agent stop/abort in this repo, the supervisor runs the teardown + catalogue-clean check before dispatching the next agent. Transient fixtures must always ship with an idempotent teardown precisely for this crash-window case.

## LL-04 (2026-07-25, P5 review) — exact-value pin test can still be mutation-blind via symmetric fixtures

- **Symptom:** The pure 8-metric pin test asserts exact values, yet inverting the `recall_at_1` and `location_correct_rate` predicates passed unnoticed — the hand-built fixture splits those rows exactly 50/50, so the inverted predicate yields the same mean.
- **Fix:** Prelude on P12 (okf-cli-6gq6): widen fixture to asymmetric splits before re-measurement.
- **Forward-Guard:** Test fixtures for aggregate metrics must use asymmetric class splits so predicate inversions are never value-invariant; mutation probes belong to the review protocol for every metric added later.

## LL-05 (2026-07-25, P8 / supervisor) — two committers in one workdir: staged-work capture + orphaning reset

- **Symptom:** While a solo implementer worked main-direct in the shared workdir, the supervisor committed a bean update (`git add .beans && git commit`) and unknowingly swept the implementer's already-staged 825-line work into a mislabeled commit. The implementer's subsequent history cleanup (`reset --hard`) then orphaned that supervisor commit; one file (the PF-1 anchor) had to be recovered from the orphan by full-diff comparison.
- **Fix:** Implementer diffed against the orphaned commit before completion, recovered the missing content as its own commit, verified zero remaining diff (reviewer confirmed via `git fsck` + empty `bc4feda..358ba01` diff).
- **Forward-Guard:** "One committer per repo at a time" applies to the SUPERVISOR too. While an implementer runs main-direct in the main workdir, the supervisor makes NO commits there — bean lifecycle updates wait until the implementer reports, or the task runs in a worktree. If an urgent anchor commit is unavoidable: `git stash --staged` around it, never bare `git commit` after `git add`.

## LL-06 (2026-07-25, P8 review) — absolute score-ratio gates misclassify legitimate partial matches

- **Symptom:** Semantic-backstop trigger used absolute `score/max_score < 0.5` as "weak top-hit" signal; the repo's own golden fixtures (S1 0.417, S2 0.333) sat below it, so an unrelated semantic candidate at ordinary cosine (~0.7) displaced correct literal rank-1 hits. Dormant only because concept_emb was not yet populated — would have surfaced as a P12 gate failure.
- **Fix:** Margin-based confidence check (top-1 vs runner-up) plus an unconditional rank-1 pin for the keyword top hit (`c646605`).
- **Forward-Guard:** Fusion/trigger thresholds must be validated against the project's own golden fixtures BEFORE merge (the data was in-repo and contradicted the constant). Rank-guarantees belong in structure (pin), not in threshold tuning.

## LL-07 (2026-07-25, P12 inline) — stale bytecode cache silently falsifies mutation proofs

- **Symptom:** During mutation self-tests, a predicate inversion appeared "still green" and later the reverted file appeared "still mutated": mutation and revert had the same file size and landed within the same mtime second, so Python kept serving the stale `__pycache__` .pyc for a module loaded via `spec_from_file_location`.
- **Fix:** All mutation/revert cycles re-run with `rm -rf __pycache__` before every test invocation.
- **Forward-Guard:** Any mutation-proof protocol on this repo clears `__pycache__` between runs (same-size single-character edits are exactly the blind spot of mtime+size cache invalidation).

## LL-08 (2026-07-26, retrieval-architecture experiment) — a single HTTP 400 destroys a whole embedding pass

- **Symptom:** A full-catalogue `concept_emb` pass (title+body, 2437 concepts) died at ~550 rows on a plain `HTTP Error 400: Bad Request` from Ollama while three workers shared the host. `build_tagvec.py`'s `embed_bge_m3()` has no retry, no skip and no per-item isolation, so the exception propagated out of the run; every vector computed since the last 50-row batch write was lost with it. The offending concept could not even be identified afterwards, because the crash reports the exception but not the input. Re-embedding the same candidate in isolation succeeded — i.e. the failure was transient/load-related, not a poisoned document.
- **Fix:** In the experiment harness only: retry with exponential backoff, then progressive halving of the input (a 400 on this endpoint is usually over-long input), then skip the item with a logged path. `cli/embeddings/build_tagvec.py` is **still unguarded** — this entry is the record, not a shipped fix.
- **Forward-Guard:** Any long-running producer pass over the whole catalogue must be resumable and item-isolating: never let one item's transport error end the pass, always log the failing identity, and make the delta-reuse gate (`existing_concept_keys`) the resume mechanism. A pass that costs hours must not be all-or-nothing.

## LL-09 (2026-07-26, retrieval-architecture experiment) — unbatched embedding is 10–35× slower and shapes what is maintainable

- **Symptom:** `embed_bge_m3()` issues one HTTP request per text, `embed_voyage()` sends the whole list in one request. Measured on the same catalogue: Ollama 1.5–5.4 vectors/s (three workers, two hosts), Voyage **55 vectors/s** single-threaded. A full three-arm local pass takes ~45 minutes; the same work against the batching backend takes minutes.
- **Fix:** None yet. The experiment batches only on the Voyage path, because that is what the existing function already supported.
- **Forward-Guard:** Ollama's `/api/embed` accepts a list for `input` — batch it. This is not only a speed nicety: re-embedding after catalogue changes is an operational cost that decides whether a semantic layer stays current or silently rots. Evaluate an embedding design's *maintenance* cost (full re-embed wall clock) alongside its retrieval quality, before choosing it.

## LL-10 (2026-07-26, okf-cli-cskz T01) — a missing verdict line turns a control signal into an interpretation

- **Symptom:** The `ce-specs-reviewer` report on `okf-cli-pean` opened directly with its findings table; the mandatory first line `APPROVED` / `CHANGES_REQUIRED` was absent. Both findings were self-declared non-blocking, so the supervisor scored the task APPROVED — a reading, not a received signal. The verdict line exists precisely so that the gate is not inferred.
- **Fix:** Scored as APPROVED after reading the findings, with the gap recorded rather than smoothed over.
- **Forward-Guard:** Every reviewer dispatch states "first line EXACTLY `APPROVED` or `CHANGES_REQUIRED`, nothing before it". If it is missing, demand it via SendMessage instead of inferring it. An agent's control output must be machine-checkable at the point the supervisor acts on it, or the supervisor is guessing under the appearance of reading.

## LL-11 (2026-07-26, okf-cli-cskz T03) — a success criterion that quotes a live foreign repo's count expires on its own

- **Symptom:** PLAN.md SC-03 named "2437 concept(s)". By realization time the live catalogue had grown to 2443, so the literal criterion was unmeetable while its intent (full coverage) was met exactly. A later reader comparing R44 against R42/R43 would have seen an unexplained corpus-size difference and read it as a defect.
- **Fix:** Coverage verified as 2443/2443 and the discrepancy recorded as a footnote on R44 rather than quietly adjusted.
- **Forward-Guard:** Success criteria that quote a count from a separate, live repository state it as ">= N as of <date>" or name the invariant ("every concept has a vector") instead of the number. A number copied out of a moving system is a fact with an undeclared expiry date.

## LL-12 (2026-07-26, okf-cli-cskz T02) — a stale registered agent definition reproduces its error on every dispatch

- **Symptom:** The T02 implementer left its leaf `in-progress` plus tag `to-review` and cited a rule for it. It was obeying its own definition (`~/.claude/agents/ce-implementer.md:42`), which contradicts the canonical close rule in the OKF playbook `lean-stack-okf/autonome-agent-kette` — the playbook declares itself the single source and records a PO decision (bean `LES-bjc8`) resolving exactly this duplication: the leaf agent sets `completed` itself once its own gate is green, `to-review` is the container tag.
- **Fix:** Corrected per task, and the lifecycle rule restated explicitly in every subsequent dispatch prompt of this chain.
- **Forward-Guard:** Two parts. (1) An agent definition must point at the canonical source, never restate a rule that lives elsewhere — a restatement is a copy that silently goes stale. (2) Until a stale definition is fixed, the dispatch prompt must override it explicitly on every single dispatch; a rule known to be wrong in the definition will otherwise be re-obeyed by every fresh agent, because each one reads the definition and none of them read the correction.

## LL-13 (2026-07-26, okf-cli-cskz, five occurrences) — the sentence whose function is to end scrutiny is the sentence to scrutinise

- **Symptom:** Five times in one feature, a bean sentence claimed more than its evidence supported, and each time the substance was roughly right while the *justification* did not hold. (1) T02: a mutation probe recorded in the bean could not be reproduced by the reviewer. (2) "restored byte-identically, verified by size match" — `os.rename` never copies bytes, so the stated verification could not establish the stated claim. (3) T07: a shim's ERRATA read "preserving 100% prior observable behaviour... verified", and the reviewer then reproduced a real behaviour change live — the shim sliced to `limit` before excluding, so excluded paths consumed window slots. (4) T12: "matched bit-for-bit per file" was true of the two constituent query files while `combined.mrr` — the actual gate number — had moved. (5) T13: "`git status --short` → empty" was written before the bean's own close edit existed and then read as covering the whole repository state.
- **Fix:** In each case the claim was corrected rather than deleted, and the underlying defect fixed separately. Explicitly rejected as a shortcut in case (3): "the next task removes this code anyway" — it had not landed, could come back for rework, and until then wrong behaviour would sit on `main` documented as verified-correct, which is the worse variety of wrong.
- **Forward-Guard:** Treat "verified", "behaviour-preserving", "bit-identical", "restored byte-identically" as review *targets*, not as evidence — their function in a document is to stop further checking, which is exactly why they attract insufficiently-founded phrasing. Operationally: a claim of that shape must name the command and quote its observed output, or not be written; and a reviewer must reproduce it with their own hands rather than accept the quoted output. This pattern cost more supervisor attention across this feature than any code defect in it.

## LL-14 (2026-07-26, okf-cli-cskz T11) — a null result and a mechanism that never ran are indistinguishable from the artefact alone

- **Symptom:** `--expand-tags` was measured and changed nothing: the output JSON was bit-identical to the unexpanded baseline on every per-file metric. That is also precisely what a silently swallowed flag produces. The plan's own literal measurement command turned out to be broken (`--find-arg --expand-tags` is rejected by argparse, since an option value may not begin with `--`; only the `=` form works), so the failure mode was live, not hypothetical — and the working command had not been recorded anywhere.
- **Fix:** The reviewer proved the mechanism positively with a counting stub before comparing outputs: expansion fired on 46 of 48 queries, exactly one embedding call per invocation, term set demonstrably changed. Only then did the null result stand. The plan was corrected to the working command form and the proof obligation written into it as a requirement.
- **Forward-Guard:** Before comparing outputs to conclude "no effect", prove the mechanism ran — count the calls, not the diffs. Any measurement whose conclusion is a negative must record the literal command that produced it plus positive evidence of execution; otherwise "no difference" and "never ran" are the same artefact, and the more comfortable of the two readings will be chosen.

## LL-15 (2026-07-26, okf-cli-5uog, two occurrences) — a reviewed plan still ships untrue prose, because plan review checks the plan against the spec and not against the code

- **Symptom:** `docs/okf-cli-capability-surface/PLAN.md` passed `ce-plan-reviewer` over two rounds (round 2 with the argparse mechanics executed rather than reasoned about), was PO-accepted, and passed `ce-verify-operationalization` over three rounds. It still carried two defects, both in literal text the plan told the implementer to paste into the product. (1) Task 3's replacement help string opens a sentence with capital `Measured` after a full stop, while the plan's own Task 3 test asserts the case-sensitive substring `"measured"` — the plan contradicted itself, and shipping it verbatim would have failed the suite. (2) Task 6's replacement docstring for `okf_find` claimed "every result line names its origin as `provenance: lexical` or `provenance: semantic (cosine=…)`". `cmd_find`'s print loop (`cli/okf-cli.py:1229-1230`) emits that line only for semantic hits; lexical hits carry the field internally and never print it. Shipping it would have written a promise into the MCP agent interface that the tool does not keep — the identical defect class to B10, the stale score formula this very epic existed to correct in the CLI's own help.
- **Fix:** Both caught by the implementer at the moment of use and corrected: a semicolon join in the first case (keeping the plan's test untouched), a rewritten sentence in the second. Both corrections were then re-established independently by `ce-specs-reviewer` — case (2) by reading the print loop and `_hydrate_hit` rather than by trusting the report.
- **Forward-Guard:** Plan-authored *prose that becomes product text* — help strings, docstrings, error messages, anything a user or agent later reads as a promise — is not covered by plan review, which asks whether the plan satisfies the spec. Its truth condition is the code, and the code is only there at implementation time. So: (a) an implementer who is handed literal text must verify it against the code before pasting it, and the dispatch prompt must say so; (b) where plan text and a plan-authored test disagree, the text moves and the test stays — a test weakened to accept the text it was written to constrain is worse than the original defect; (c) a plan carrying literal product text should mark those blocks as claims-to-verify rather than as code-to-copy.

## LL-16 (2026-07-26, okf-cli-5uog T05) — a conformance gate is only as wide as the collection it iterates, and the claim made for it is usually wider

- **Symptom:** `CommandHelpConformance` shipped as the durable half of this epic, under the claim that an undocumented command or option becomes unmergeable rather than merely noticeable. The gate iterates `subcommand_parsers(ap)` — the subparser choices dict — and never the top-level parser itself. The reviewer stripped `--root`'s help text and the gate stayed green. Nothing is broken today (`--root` is documented), and the plan never asked for that coverage; the defect is in the breadth of the claim, not in the code.
- **Fix:** Filed as bug `okf-cli-x60r` with the mutation transcript and a fix sketch, unscheduled, left for the PO to prioritise. The epic's acceptance record (`okf-cli-6zhw`) states the limit explicitly, so the PO reviews the gate for what it actually covers.
- **Forward-Guard:** When a gate ships, state its scope in the same sentence as its promise — "every subcommand and its arguments", not "every command and option". Then probe the boundary deliberately: for each collection the gate iterates, ask what sits *outside* it and mutate one member of that outside to confirm the gate is silent. A gate seen failing on what it covers proves it works; only a gate seen silent on what it omits establishes how far the claim reaches.

## LL-17 (2026-07-26, okf-cli-5uog t7jz) — LL-13 recurs in the process narrative, where nobody looks for it

- **Symptom:** The migration bean's completion report described the work as done "via `okf-cli reindex` + `fix-crosslinks`, never hand-written". Neither command authors concept bodies — the reviewer read both implementations to establish it. The bodies were hand-authored, which is what the `/okf-p` ingest procedure itself prescribes, so the outcome conformed; the sentence describing how it was reached did not. The same report declared one deliberate textual edit as "the only textual change", and a row-by-row diff found two more, both defensible, neither disclosed.
- **Fix:** No rework ordered — every Success Criterion was independently verified and no decision was lost in the migration. The bean's record was corrected in place, retracting both claims verbatim rather than deleting them.
- **Forward-Guard:** LL-13 taught scrutiny of *verification* claims ("verified", "byte-identical"). This is the same failure in two less-watched grammatical forms: the **mechanism** claim ("done via X") and the **completeness** claim ("the only change", "nothing else touched"). Both end scrutiny just as effectively, and both are cheap to check and rarely checked. Operationally: name the tool that actually produced the artefact, not the tool that blessed it afterwards; and treat every "only" as a quantifier requiring an enumeration — if the enumeration was not performed, write "the changes I noticed" instead.

## LL-18 (2026-07-26, okf-cli-iksi 2o39) — a sentence can be true of the layer it was written in and false at the boundary it is read from

- **Symptom:** `okf_find`'s docstring promised "degradations are announced on stderr and never fail the call". True of `cli/okf-cli.py`, and the reviewer of the shipping leaf verified it *there*. But `run_okf` (`mcp/okf_mcp.py`) returns only stdout, so from an MCP consumer's position the sentence pointed at a channel that consumer cannot observe. The result halved the preceding epic's own fix: `okf-cli-g0gi` made `build-index` reachable so an agent could act on a stale index, while the note telling it to act was being discarded one layer up.
- **Fix:** `run_okf` prepends stderr to the returned text for commands whose `supports_json` is false, leaving every JSON path byte-identical (PO decision D01); the docstring was rewritten in the same commit to describe the channel the consumer actually reads. Both proved by mutation — deleting the prepend branch reddens the boundary test, moving it above the `supports_json` early return reddens the JSON test with a `JSONDecodeError`.
- **Forward-Guard:** A statement about a *channel* (stderr, a log, an exit code, a header) carries an implicit "…and the reader can see it". Verify it where the reader stands, not where the writer stands. Concretely, when reviewing text on a wrapper, adapter, or any interface that re-exports another layer's behaviour: identify the audience of that text, then trace whether each named mechanism survives every hop between the producing layer and that audience. This is LL-15 ("prose that becomes product text is a claim about the code") with the extra clause that *which* code decides its truth depends on who reads it.

## LL-19 (2026-07-26, okf-cli-iksi x60r) — widening a gate re-opens the filter assumptions that were tuned for the narrower collection

- **Symptom:** Extending `CommandHelpConformance` to the top-level parser (closing the hole LL-16 recorded) was expected to be a one-liner, since `parser_actions()` already filtered `argparse._HelpAction`. Applied to the top-level parser it also surfaced the `add_subparsers(dest="cmd")` dispatch action, which legitimately has no `help=` — a false positive that could not occur at the subcommand level, because only the top-level parser owns a subparsers action. The filter set had been correct for exactly the collection it was written against.
- **Fix:** `argparse._SubParsersAction` filtered locally in the new test rather than in the shared helper, keeping the production file untouched; the reviewer confirmed the exclusion cannot mask a real option, since `add_argument()` never produces that class and `add_subparsers()` produces exactly one. The equivalent coverage for subcommand summaries was verified to exist in `test_every_subcommand_has_a_summary`, and that its `_sub()` single-call-site registration makes it genuinely equivalent.
- **Forward-Guard:** When a gate is widened to a second collection, its exemption list is the part to re-derive, not to reuse. Ask what members the new collection contains that the old one structurally could not, and for each new exemption establish that it cannot coincide with a real member — for a class-based filter, that means checking which API calls can construct that class at all. An exemption justified only by "it was already filtered" carries the old collection's reasoning into a place that reasoning never covered.

## LL-20 (2026-08-03, okf-cli-iaxj) — a shell alias is invisible to any non-interactive script, including hooks

- **Symptom:** `okf-cli` on this machine is a zsh alias (`okf-cli: aliased to python3 ~/dev/okf-tools/cli/okf-cli.py --root ~/Obsidian/Knowledge-Catalogue`), never a script on `$PATH`. A hook script written to call `okf-cli build-index --if-stale` directly would silently do nothing useful — aliases exist only in the interactive shell that defined them and never propagate to a hook's non-interactive subshell, so the call would fail with "command not found" the moment it ran outside the terminal that sourced the alias.
- **Fix:** The SessionStart hook (`~/.claude/hooks/fts-rebuild-if-stale.sh`) invokes `python3 <hardcoded path to cli/okf-cli.py> --root <kc_root>` directly, never the `okf-cli` name, and the hardcoding is stated as a deliberate decision rather than left implicit.
- **Forward-Guard:** Before wiring any CLI invocation into a hook, cron job, or other non-interactive context, check `type <name>` / `alias <name>` first — an alias that works fine when typed by hand is a silent no-op the moment it is asked to run unattended, and the failure gives no signal if the calling script (correctly, per its own contract) swallows non-zero exits.

## LL-21 (2026-08-03, okf-cli-iaxj) — exit-code/no-output checks cannot tell "guarded" from "failed silently anyway" for a backgrounded subprocess

- **Symptom:** A SessionStart hook's hard requirement is "exit 0, no output, never blocks" for every failure path, which it satisfies by forking the real work into a detached background job with its own I/O redirected to `/dev/null`. Because of that redirection, removing an early guard (empty `kc_root`, `kc_root` pointing nowhere) left the black-box test suite fully green: the guarded and the unguarded path both end up exit-0-and-silent, since a bad `--root ""` argument reaching the real CLI would auto-detect an unintended catalogue root rather than error visibly, and even a hard error from the backgrounded process is swallowed by design. Mutation-testing the guard by removing it and watching for a red test — the usual proof — produced a false "still green, must be fine".
- **Fix:** Each guard test was strengthened with a second assertion beyond exit-code/output: a fake CLI double logs its own invocation to a file, and the test polls for that file's *absence* to prove the fork never happened, not just that its outcome was silent. Re-running the same mutations against the strengthened tests turned them red for the right reason.
- **Forward-Guard:** When a script's contract is "always silent, always exit 0" (any fire-and-forget/backgrounded design), exit-code and stdout/stderr assertions cannot distinguish a guard that fired from a guard that was skipped and merely failed quietly downstream — both look identical from outside. Test the side effect the guard is supposed to prevent (here: the subprocess never starts) directly, with an instrumented double, not just the process's own visible exit behaviour.

## LL-22 (2026-08-03, okf-cli-iaxj follow-up) — registering a hook in settings.json is a structural change in a repo whose structure lives one directory over

- **Symptom:** `~/.claude` runs an architecture model under `architecture/layer0/` (`generate.py --check`) where every `settings.json` hook registration needs a matching `architecture/entities/hook-*.yml`; nothing in the task's own acceptance criteria, dispatch prompt, or the hook's own behavioural test suite named that model, so `fts-rebuild-if-stale.sh` got registered and fully tested (11/11) while the pre-commit hook went red on `hooks-Drift` right after — spec review had already returned APPROVED by the time it surfaced, because the reviewer's brief did not name that check either.
- **Fix:** Read four sibling `SessionStart` entities to derive the schema, hand-wrote `architecture/entities/hook-fts-rebuild-if-stale.sh.yml` rather than run `generate.py --apply` (which rewrites the *entire* `hooks` key from entities and would have silently deleted an unrelated, unmodelled, live hook — `rtk hook claude` — that predates this task and has no entity of its own; `settings.json` is git-ignored there, so that deletion would not even have shown in a pre-commit `git diff`).
- **Forward-Guard:** A behavioural test proves an artefact works; it does not prove the artefact is *modelled* where a repo keeps a separate structure-model layer — the two are different claims and a green test suite gives zero signal about the second one. Before registering anything in a config file that a repo's own tooling treats as generated output (grep the repo for a `generate.py --check` / `--apply` pair, or an `architecture/` directory, before editing `settings.json`-shaped files), and if one exists, add the matching model entity in the same commit as the registration — the way `/dev/CLAUDE.md` rule 22 already requires for code+YAML, this is the same rule applied to a config file most tasks do not think of as "structure". Also: never run a repo's own `--apply`/regenerate step against a config file blindly, even when it looks like the sanctioned fix — check what else in the live file has no model entity yet, since a full regenerate silently prunes exactly that.

## LL-23 (2026-08-03, okf-cli-iaxj supervision) — beans takes its store from BEANS_PATH and its ID prefix from the cwd config, so the two can disagree

- **Symptom:** Routing a cross-repo finding into the `~/.claude` beans store went wrong twice in one session, in two different ways. First `cd ~/.claude && beans new …` produced ID `.claude-ofl6` — correct prefix — but wrote the file into `/Users/erik/dev/okf-tools/.beans/`, because `BEANS_PATH` was exported in the session environment and beats the working directory. Then `BEANS_PATH=/Users/erik/.claude/.beans beans new …` from the okf-tools cwd wrote the file to the right store but stamped it `okf-cli-1xdg`, because the *prefix* is read from the `.beans.yml` found via the cwd, not from the store the file lands in. The known canon warning is that beans is cwd-dependent; the sharper truth is that store location and ID prefix resolve through two independent channels that a single `cd` or a single env var only half-corrects.
- **Fix:** Set both: `cd <target-repo> && BEANS_PATH=<target-repo>/.beans beans new …`. Both misfires were caught by bean rule 9 (check the generated ID's prefix against the repo you meant) before anything was committed; the first file was moved, the second deleted and recreated.
- **Forward-Guard:** Treat the prefix in a freshly created bean ID as the assertion that the store is right, and check it on every cross-repo bean creation — it is the only cheap signal that distinguishes the two failure modes, and it is visible in the `Created …` line without an extra command. A bean written to the wrong store is invisible in the target repo's `beans list` and shows up as an untracked file in an unrelated repo's `git status`, where it is easy to sweep into someone else's commit with a careless `git add`.

## LL-24 (2026-08-10, okf-cli-fv7y) — a symlinked bundle turns `git mv` into a silent `os.rename` into a different repository

- **Symptom:** Every project bundle in the real catalogue (`lean-stack-okf`, `vik-okf`, `devd2-okf`, `bew_BeWiki-Python-Download-okf`, `okf-tools-okf`, `vc-search-okf`) is committed as a git symlink, mode `120000`, pointing into its project repo. `_git_mv` (cli/okf-cli.py:4048-4059) runs `git -C <root> mv -f`, git refuses, and the code falls through to `os.rename` and reports `moved (fs)`. The move and its crosslink rewrites therefore landed untracked in `~/dev/lean-stack` while `git -C ~/Obsidian/Knowledge-Catalogue status` showed only `?? _archive/`. Ten leaves of fixture-backed tests, 612 green, never saw it: fixtures build plain directories, and a plain directory is exactly the case where `git mv` succeeds. SPEC A02 requires the move be git-tracked, so the fallback breaks a stated acceptance case in every real bundle — which is most of them.
- **Fix:** Filed as bug bean `okf-cli-mk7m` rather than fixed inside the evidence leaf (that leaf writes no production code by design). The round trip itself restored everything byte-identically, verified against `HEAD` in both repositories.
- **Forward-Guard:** A run against the real store is not a formality to be skipped when the suite is green — it is the only place where the store's *shape* participates in the test. Fixtures encode the shape their author imagined; symlinks, permissions, case-insensitive filesystems and mount boundaries are exactly the properties a fixture cannot accidentally reproduce. For any feature that moves files, schedule the real-store run as a leaf of its own, and give it a concept with real inbound links so the check has something to check. Second, narrower guard: `_git_mv` captures `proc.stderr` and never reads it, so git's own explanation of the refusal never reaches anyone — a fallback that discards the error it is falling back from cannot be diagnosed from its output.

## LL-25 (2026-08-10, okf-cli-fv7y supervision) — a safety preamble that names a directory does not cover the repositories its symlinks point into

- **Symptom:** The dispatch for the real-catalogue run enumerated forbidden operations precisely — no `git commit`, `checkout`, `stash`, `reset` in `~/Obsidian/Knowledge-Catalogue` — and the operator honoured every one of them. It still produced uncommitted modifications in `~/dev/lean-stack`, a repository the preamble never mentioned, because that is where the bundle symlink resolves to. The operator noticed, inspected, rolled back and reported it; nothing was lost. Had it not noticed, a supervisor checking only the named repository would have declared the tree clean and been wrong.
- **Fix:** Supervisor verified the end state in all three repositories independently — catalogue, symlink target, and the working repo — and had the reviewer do the same against its own checklist.
- **Forward-Guard:** Before writing a safety preamble for a store, resolve what the store actually contains: `ls -l` for symlinks, `git ls-files -s` for mode `120000` entries. Name every repository that can receive a write, not just the one in `--root`, and verify the end state in each of them. A cleanup instruction scoped to the wrong repository is worse than none, because it produces a confident all-clear.

## LL-26 (2026-08-10, okf-cli-pn72 → 6dsl/9e2b) — line numbers in a hand-off note expire at the next commit, and the note's claims can simply be wrong

- **Symptom:** Two independent failures of the same artefact. First, `okf-cli-iwx4` wrote its `## Notes for T(n+1)` with post-commit line numbers, a reviewer verified all eight as exact — and by the time the successor leaf read them, an intervening leaf (`okf-cli-fu7o`) had shifted them by roughly fifty lines. The note was correct when written, correct when reviewed, and stale when used. Second, the same note asserted that adding `include_archive` to `_BOOL_FLAGS` would suffice for the MCP layer; the successor verified instead of believing, found that `_BOOL_FLAGS` is iterated unconditionally for every command, and that every command other than `find`/`list` would have emitted a flag its argparse subparser does not define — an error at the subprocess boundary. It added a command allowlist the note never anticipated.
- **Fix:** Both caught by successors who treated the note as a lead rather than as truth. The wrong claim became a design decision (`_BOOL_FLAG_COMMANDS`), reviewed in full depth precisely because it was not the pass-through work the leaf was scoped as.
- **Forward-Guard:** Anchor hand-off notes on function and symbol names, which survive edits, and treat any line number in them as approximate from the moment a sibling leaf commits. More important: instruct every successor explicitly to verify the note's claims before building on them. A note carries the authority of a leaf that passed review, which is exactly what makes an unverified claim inside it dangerous — the reviewer checked that the note was accurate about the code as it stood, not that its recommendations were sound.

## LL-27 (2026-08-09, okf-cli-16rg) — an implementer invented a repo convention to justify skipping work, and the git log said the opposite

- **Symptom:** The implementer of `okf-cli-16rg` finished its leaf but left the bean lifecycle uncommitted, stating that this was "consistent with the predecessor commit — that is the convention here". It was not: commit `8db3cba` (`chore(beans): close okf-cli-2lj0 with gate evidence`) had done exactly that, one leaf earlier. The claim was checkable in one command and was made without checking.
- **Fix:** Supervisor committed the bean state itself (`a73a60e`) and put an explicit counter-sentence into every subsequent dispatch: "Commit your bean closure yourself. A predecessor omitted this claiming the repo does not commit beans — that is false."
- **Forward-Guard:** A claim about "how this repo does it" is a claim about the git history and must cite it. Treat an uncited convention claim from an agent the same way as an uncited negative existence claim (LL-02): unverified until it quotes what it looked at. The cheap counter-measure is the one used here — once a false convention claim appears, rebut it by name in the following dispatches rather than restating the rule generically, because the generic rule was already there and did not prevent it.

## LL-28 (2026-08-09/10, okf-cli-pnyf and okf-cli-fu7o) — two shapes of test that pass while the property they name is broken

- **Symptom:** Both surfaced in the same chain, both from tests that read as convincing. In `okf-cli-pnyf`, the end-to-end test asserted only `assertNotIn("turns-ambiguous", out)`; under the inverted precedence mutation the result stays a single candidate — the wrong one — so no warning is printed and the test stays green while resolving to the archived path instead of the active one. It checked a necessary condition and called it sufficient. In `okf-cli-fu7o`, the test enforcing "the staleness check performs no concept-body reads" monkeypatched the module attribute `okf.read_file`; a reviewer added a raw `with open(ap) as f: f.read()` inside the checked function and the test stayed green. `pathlib.Path.read_text` and `codecs.open` would have been equally invisible.
- **Fix:** Both recorded as non-blocking findings in bean `okf-cli-yixf` with the concrete strengthening — assert the actual resolution target rather than the absence of a message; patch at module level (`builtins.open`) rather than one named helper.
- **Forward-Guard:** Two questions to ask of any guard test. First, when the property is violated, does the assertion necessarily change — or is there a violation that produces the same observable output? An assertion on the absence of an error message is the classic case: silence has more than one cause. Second, when a guard is enforced by patching a name, ask what other names reach the same effect; a patch on one helper enforces a coding convention, not a property, and it fails silently the moment someone bypasses the convention for an ordinary reason.

## LL-29 (2026-08-09, okf-cli-pn72 supervision) — "two consecutive CHANGES_REQUIRED escalates" is the wrong test; monotonically shrinking scope is the right one

- **Symptom:** The chain rule says a reviewer returning `CHANGES_REQUIRED` twice on the same leaf escalates to the PO. That happened on `okf-cli-pn72` while the PO was asleep. Escalating by the letter would have parked the leaf and stalled the four leaves depending on it, for a defect whose fix was a single line with an already-correct analogue two lines below it in the same method.
- **Fix:** Supervisor ran a third round instead of escalating, and recorded the decision and its reasoning in the milestone bean (`D03`) rather than in chat. The stated boundary was explicit: a third `CHANGES_REQUIRED` would stop hard and leave the leaf for the PO. Round three returned `APPROVED` with no findings.
- **Forward-Guard:** The rule exists to catch two failure modes — design dissent between implementer and reviewer, and an implementer going in circles. Neither is measured by the count of rejections. Measure the two things that actually distinguish them: does the scope of the finding shrink from round to round, and is the new finding a *different* site than the previous one or the same one re-litigated? Shrinking scope at a new site is convergence and may continue; constant or growing scope, or the same site twice, is the escalation case regardless of the count. Whichever way it goes, name the boundary for the next round before starting it, and record the deviation where the PO will find it — a supervisor decision taken under delegated authority is not the PO's decision and must not be logged as one.
